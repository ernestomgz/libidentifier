# Approved Stage 2 boundaries

- Independent Python API with LIEF; no mandatory full Androguard framework.
- Preserve CLI scanner discovery and graceful missing-scanner fallback.
- CLI may provision only wholly absent advisory databases unless `--offline`.
  Existing databases require explicit update. Actual assessment is always offline;
  Python scan/correlation never download. No submitted code execution.
- Reliability and evidence precede grouping and component relationships.
- Direct POM dependencies/simple properties first; preserve unsupported resolution.
- Bounded declared invocation references, not runtime dispatch or full call graphs.
- Separate release, artifact, variant, fingerprint and occurrence internally;
  explicit database version/rebuild, with R8 generation deferred to Stage 3.
- Preserve existing APIs, JSON semantics and compact CLI; new fields have defaults.
- Stage 3 quality targets are provisional; measure exact-version coverage separately.

## Implementation choices

Pinned LIEF supplies parsing and method bytecode, but does not expose interfaces
or canonical type descriptors directly through its Python class API. A bounded
DEX table reader supplements it; extraction is still validated through LIEF.
Bytecode bytes alone cannot identify safe instruction boundaries. Adding full
Androguard solely for references is outside the approved dependency scope; no
lightweight third-party decoder has been qualified. The initial implementation
therefore uses a small original width/payload traversal with ordinary invocation
resolution and explicit partial results, tested against all ten ordinary forms,
switch/array payloads, invalid indexes and truncated/special instructions. It is
replaceable internally without changing relationship records.

The reference store retains multiple artifacts/variants/algorithms, but Stage 2
structural scoring uses the first imported DEX variant per release. It does not
sum correlated variant matches; improved selection/fusion belongs in Stage 3.
POM parents, BOMs and dependency-management context are retained as original XML
and limitations; no Maven process, parent fetching or effective-model inference
is needed for the initial direct-declaration capability.
